## Autosave and native persistence

**自動儲存：開** is the default. The compact header checkbox persists only its small on/off preference in localStorage, scoped by the isolated-test nonce when configured. Disabling it does not disable manual Save or recovery. Automatic saves require an initialized, committed identity (revision > 0) and a bound native `.tws.json` handle. Brand-new and unbound CSV/XLSX imports do not open pickers or auto-create external files; their first explicit Save establishes binding.

Actual persisted user/model mutations restart a **3,000 ms** trailing timer. Selection/navigation, hydration, document editing intermediates, formula mutation events, and engine-only `set-range-values` remain excluded by the existing classifier. Formula results are still included when a real mutation's complete snapshot is saved. Snapshots are not captured/serialized on each keystroke.

One per-open-workbook coordinator serializes automatic and manual requests through the **same existing native persistence pipeline**:

1. Query the bound file's write permission, without requesting permission from timers.
2. Commit the complete snapshot with `expected_revision` through the existing API. SQLite and the managed mirror retain the existing transaction/rollback/verification contract.
3. Retrieve the committed native document.
4. Write and read-back verify the bound user file, with permission prompting disabled in the persistence stage.
5. Report **已儲存** only if all required targets succeeded and no newer generation exists. A newer edit stays **未儲存** and schedules a subsequent save.

Manual Save starts any necessary picker/authorization from the click, then flushes the coordinator. A pending autosave is accelerated. A manual request during an active save joins its drain; newer edits cause a subsequent serialized save before the manual request reports success. No parallel conflicting PUTs are generated by this coordinator. Separate application instances remain protected by backend optimistic concurrency.

CSV/XLSX are exchange operations and are never automatically exported. Their existing conversion/security limits and formula policy are unchanged; autosave is held while exchange dialogs/processes are active.

## Failure, permissions, and conflicts

Failed autosave pauses automatic retry, including after subsequent edits. Local edits remain visible and recovery keeps checkpointing. Press **儲存** for explicit retry. Toggling autosave does not clear a failed/conflicted save block; explicit successful Save is required. There are no repeated permission prompts or success toasts.

Unavailable backend, SQLite failure, or managed-mirror failure cannot advance a successful revision or write the external copy. Permission loss before commit leaves the last internal commit intact and keeps unsaved edits in browser recovery. If permission/disk/verification fails after internal commit, that committed recovery copy remains intact but the status is permission-required/external-failed, not saved. Same-generation external retry verifies that the internal native document still matches before writing the pending copy; a changed revision is refused.

HTTP **409** is explicitly reported as **儲存衝突**. The base revision is never automatically replaced to force an overwrite. Restore of a stale checkpoint keeps its original base revision; use Save As to preserve it as a separate identity instead of overwriting a newer workbook.

The existing **儲存並繼續 / 放棄變更 / 取消** navigation dialog remains. Save-and-continue proceeds only when the manual drain reaches the latest state successfully. A separate active-save flag keeps discard/switching blocked even if an edit changes the display from saving to unsaved. Discard cancels pending timers and removes that workbook's recovery record. Cancelling a subsequent native picker leaves the committed original workbook available rather than leaving a disposed autosave coordinator.

Save As pauses the old timer and creates a new identity through the existing copy pipeline. The new identity never reads the original's recovery key. Edits made during copy commit are transferred as unsaved edits to the new model, with a new-identity checkpoint where storage is available; they are not replaced by the older copy snapshot. The original's checkpoint remains associated with the original, whose committed contents were not changed by copying.

## IndexedDB recovery

Full snapshots are stored in **IndexedDB**, never in localStorage. The recovery database is browser-origin isolated and additionally named with the configured test nonce (or `manual`). Each workbook ID has at most one latest checkpoint containing:

- Workbook ID, base revision, and base committed update timestamp.
- Checkpoint timestamp, per-open-session UUID, and mutation generation.
- A structured cloned complete snapshot and its UTF-8 JSON payload size.

Recovery writes debounce **500 ms**, with a **2,000 ms** maximum wait during continuous edits. Transactions resolve only on IDB transaction completion, not request success. A small budget store tracks capacity without cloning all other workbooks' full snapshots on every checkpoint; budget and checkpoint updates commit atomically. The ordered store queue prevents an older queued checkpoint from reappearing after save cleanup. Successful full saves acknowledge only the saved session/generation; newer edits or another session's record are not deleted. Newer edits made during save are rebased/checkpointed against the successful commit before old-generation cleanup. Failed saves retain/refresh local recovery instead.

Opening compares identity, expiry, snapshot contents, base revision, and base committed timestamp. Identical/expired checkpoints do not replace the workbook. A differing record produces **偵測到未完成儲存的復原資料**:

- **復原**: load the checkpoint into Univer as dirty, recalculate formulas, and preserve its base revision. A stale-base checkpoint explicitly warns and blocks automatic save.
- **使用已儲存版本**: acknowledge the selected checkpoint and load committed contents.
- **取消**: return to the list without deleting the checkpoint.

Delete removes the deleted workbook's recovery record. Cleanup failure is visible. Workbooks and isolated nonces never share recovery keys.

## Bounds and shutdown limitations

- Latest checkpoint only per workbook.
- **16 MiB** per snapshot payload, **64 MiB** aggregate snapshot payload, **32** retained workbook records.
- Expired/invalid records are pruned during later writes; records expire after **seven days**. Live records are not silently evicted to make room: capacity failures are shown and manual Save is recommended.
- Browser quota/eviction/private-mode restrictions can prevent recovery. IDB is local convenience recovery, not backup or guaranteed durable enterprise storage.
- A crash inside the 500 ms checkpoint window, before the IDB transaction commits, or during unavailable/quota-exceeded storage can lose the latest uncommitted edit. Continuous-edit max-wait is bounded scheduling, not a hard real-time guarantee.
- `beforeunload` protects dirty and actively saving data where browsers permit it. No asynchronous network save/checkpoint is assumed to finish during shutdown.
- The application still needs the backend to load the committed workbook before offering recovery; this is not a full offline editor.
- One latest checkpoint per workbook is shared by tabs of the same origin/nonce. It is not a multi-tab edit history; simultaneous different unsaved versions are not independently archived. Backend revisions still protect committed storage.
